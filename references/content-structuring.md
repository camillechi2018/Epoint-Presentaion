# 材料结构化与正文选稿

材料读取产出的段落、表格和来源清单由当前 Agent 整理成逐页内容，随后交给现有组件选稿。此步骤适用于所有 Agent 平台，不需要用户手工填表，不调用额外模型服务。

## Agent 必须完成的整理

1. 从事实清单辨认真实条目、说明、指标数值/单位/时期、步骤顺序及引用来源；保留否定、约数、计划/已完成状态等限定条件。
2. 先选择内容关系，再组织字段：普通并列用 cards 的 title/body；指标、表格、流程等使用现有对应输入类型，不把所有材料统一写成 bullets。只在材料确有关系时选择流程、层级或循环。
3. 并列原文若仍以字符串列表存在，为每条提炼一个中性短标题，放入同位置的 `content.item_titles`。原来的 `content.items` 正文保持不变。标题是 Agent 基于材料提出的表达，不是程序证明的事实，提交前须检查没有新增业务结论。
4. 根据候选容量再确定分组和分页；不得为固定项数凭空拆成更多业务点。暂时放不下时保留事实，换版或拆页。本轮准备工具不压缩正文、不改项数、不使可选字段失效。

## 内容准备入口

```text
<Python> scripts/run.py --structure-content --request <逐页草稿.json> --out <整理后请求.json> --report <整理报告.json>
```

使用安装器登记的解释器，与材料读取和选稿入口一致。输出路径必须为新文件，不能覆盖源请求。

并列条目的最小示例（仅展示正文页，结构页仍按原规范准备）：

```json
{
  "theme": "blue",
  "complete_deck": false,
  "pages": [{
    "page_id": "overview",
    "role": "body",
    "purpose": "介绍项目情况",
    "title": "项目情况",
    "information_relation": "parallel-points",
    "source_refs": ["本次事实清单中的真实来源引用"],
    "content": {
      "type": "bullets",
      "items": ["约200人参与，计划2027年部署。", "目前尚未通过验收。"],
      "item_titles": ["人员与计划", "验收状态"]
    }
  }]
}
```

工具输出 `cards`，每项含 title 和逐字保留的 body，并保留页面来源及字段转换记录。已是结构化 cards/metrics/process/table 等输入直接沿用，仍由对应选稿与填充规则验证；准备步骤不宣称已经完成全部业务校验。

没有短标题、条目与标题数量不符、或文字被声明为流程/层级等关系时，报告返回 `needs_agent_structure` 和具体 `tasks`；输出是供继续编辑的草稿，退出码为 2。Agent 应按任务补齐标题或改成真实的对应结构，再运行准备步骤。不得为了消除待办，把流程改成并列或从原文任意截几个字当标题。

法律条款、原文摘录等确实适合逐条展示时，允许在 content 中填写 `keep_bullets_reason`，例如“逐条保留原始条款措辞”；工具保留 bullets 并记录理由。无需为追求模板率强行卡片化。

报告 `ready_for_matching` 只表示没有此步骤的待办。接下来运行常规 `scripts/run.py --request ... --plan-out ... --out ...`；字段齐全、容量合格、实际填充、最终渲染各有独立检查。

## 旧请求兼容

正式选稿入口也会调用内容准备：已有 item_titles 的并列列表直接规范化，缺标题的旧列表保持原数据，并在预检报告 `content_preparation.tasks` 中提示可优化事项。旧请求不会仅因缺 item_titles 被阻断；其正常选稿和回退规则继续运行。准备程序不改变业务语义约束、容量或模板验收状态。

## 与页标题/Logo 解耦的关系

材料结构化负责“内容是什么、各条信息是什么关系、正文如何分组”；公共页眉解耦负责“页标题和 Logo 放在哪里、由哪个框架管理”。两者都帮助组件复用，但职责不同。

正文内部的小标题、中心论点和字段属于组件内容；页面顶部标题和 Logo 属于公共框架。不能为了复用组件把内部中心论点当成公共标题一并删除。当前准备工具只使用现有整页组件调用方式，未来可继续把其输出交给正文派生组件。
